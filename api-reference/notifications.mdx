title: "Notifications API and real-time SSE stream"
description: "List and update notification endpoints plus an SSE stream endpoint for real-time in-app delivery of trigger results and system events."
---

The notifications API lets you retrieve and manage notifications generated by lead triggers, system events, exports, and CRM syncs. In addition to the REST endpoints, CVR-MATE exposes a Server-Sent Events (SSE) stream at `/api/notifications/stream` so that browser clients can receive notifications in real time without polling.

## Endpoints

| Method | Path | Description |
|--------|------|-------------|
| `GET` | `/api/notifications` | List notifications for the authenticated user |
| `GET` | `/api/notifications/[id]` | Get a single notification by ID |
| `PATCH` | `/api/notifications/[id]` | Mark a notification as read |
| `POST` | `/api/notifications/read-all` | Mark all notifications as read |
| `GET` | `/api/notifications/stream` | SSE stream for real-time notifications |

---

## GET /api/notifications

Returns notifications for the authenticated user, ordered by `createdAt` descending (newest first).

### Query parameters

<ParamField query="unread" type="boolean">
  When `true`, returns only unread notifications (`isRead: false`). Omit or set to `false` to return all notifications.
</ParamField>

<ParamField query="type" type="string">
  Filter by notification type. One of:
  - `"trigger"` — lead trigger fired and matched companies
  - `"system"` — platform announcements and alerts
  - `"export"` — export jobs completed or failed
  - `"crm_sync"` — CRM synchronisation events
</ParamField>

### Response

<ResponseField name="notifications" type="array">
  Array of notification objects.

  <Expandable title="Notification object fields">
    <ResponseField name="id" type="string" required>
      UUID of the notification.
    </ResponseField>

    <ResponseField name="type" type="string" required>
      Notification type: `"trigger"`, `"system"`, `"export"`, or `"crm_sync"`.
    </ResponseField>

    <ResponseField name="title" type="string" required>
      Short notification title displayed in the inbox.
    </ResponseField>

    <ResponseField name="message" type="string | null">
      Optional body text with additional detail.
    </ResponseField>

    <ResponseField name="isRead" type="boolean" required>
      Whether the notification has been read.
    </ResponseField>

    <ResponseField name="link" type="string | null">
      URL to navigate to when the notification is clicked. `null` if no destination is associated.
    </ResponseField>

    <ResponseField name="priority" type="string" required>
      Display priority: `"low"`, `"normal"`, `"high"`, or `"urgent"`. Higher-priority notifications may be surfaced more prominently in the UI.
    </ResponseField>

    <ResponseField name="createdAt" type="string" required>
      ISO 8601 timestamp when the notification was created.
    </ResponseField>
  </Expandable>
</ResponseField>

## GET /api/notifications/[id]

Returns a single notification by its UUID.

Returns HTTP `404` if the notification does not exist or does not belong to the authenticated user.

---

## PATCH /api/notifications/[id]

Marks a notification as read. Currently the only supported mutation is toggling `isRead`.

### Body

<ParamField body="isRead" type="boolean" required>
  Pass `true` to mark the notification as read. Passing `false` marks it as unread.
</ParamField>

### Example

```bash
curl -X PATCH https://your-domain.com/api/notifications/uuid-here \
  -H "Content-Type: application/json" \
  -b cookies.txt \
  -d '{"isRead": true}'
```

---

## POST /api/notifications/read-all

Marks every unread notification belonging to the authenticated user as read in a single operation. Useful when implementing a "mark all as read" button.

Returns HTTP `200` with `{ "success": true }` on success. No request body is required.

## GET /api/notifications/stream

Opens a persistent Server-Sent Events connection. The server pushes notification events as they are created, eliminating the need for client polling.

### Connection

Connect from the browser using the native `EventSource` API, or from any HTTP client by setting the `Accept: text/event-stream` header. The connection remains open until the client disconnects or the server closes it.

### Event types

**`notification`** — emitted whenever a new notification is created for the authenticated user. The event `data` is a JSON-serialised notification object with the same fields as the REST response.

**`heartbeat`** — emitted periodically (approximately every 30 seconds) to keep the connection alive through proxies and load balancers. The `data` field contains an ISO 8601 timestamp. Clients can ignore this event.

### Browser example

```javascript
const es = new EventSource('/api/notifications/stream');

es.addEventListener('notification', (event) => {
  const notification = JSON.parse(event.data);
  console.log('New notification:', notification.title);
});

es.addEventListener('heartbeat', () => {
  // Connection is alive — no action needed
});

es.onerror = () => {
  // EventSource reconnects automatically on disconnect
};
```

### Reconnection

The browser `EventSource` API reconnects automatically when the connection drops. Each reconnection re-authenticates using the session cookie; no token refresh is needed.

<Note>
  The SSE stream uses an in-process event emitter to fan out notifications to connected clients. In a single-instance deployment this works correctly. In a **multi-instance or horizontally scaled** deployment, a client connected to instance A will not receive events emitted on instance B. For multi-instance setups, replace the in-process fan-out with a Redis pub/sub channel so that all instances broadcast to all connected clients.
</Note>
